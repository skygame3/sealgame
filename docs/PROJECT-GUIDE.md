# SEAL 프로젝트 가이드

_이 문서를 처음 읽는 사람을 위해 — 개념 설명부터 시작합니다_

---

## 이 문서는 왜 있나요?

이 프로젝트에는 이미 여러 기술 문서가 있습니다(`design-spec.md`, `game-rules.md`, `memory/decisions.md` 등).
하지만 그 문서들은 "이미 프로젝트를 아는 사람"을 대상으로 쓰여 있어서,
처음 보는 사람은 어디서부터 읽어야 할지 막막할 수 있습니다.

이 문서는 **개발 경험이 적은 사람도** SEAL이 뭐고, 왜 이렇게 설계했는지,
어디서부터 코드를 보면 되는지 이해할 수 있도록 쉬운 말로 풀어씁니다.
더 깊은 내용이 필요하면 각 섹션 끝에 "더 알고 싶다면" 링크를 달아뒀습니다.

---

## 1. SEAL이 뭔가요?

SEAL은 2명이 즐기는 추상 전략 보드게임입니다. 체스나 바둑처럼 판 위에 돌을 놓는데,
독특한 점은 **판 자체가 게임 중에 변한다**는 것입니다.

- 상대 돌을 **포획**하면, 그 자리가 **봉인**되어 아무도 못 씀
- 포획할 때마다 **결정(💎)**이라는 자원을 얻음
- 결정을 모으면: 돌을 더 놓거나, 봉인을 풀거나, 막혀있던 새 칸을 열 수 있음
- 게임이 끝나면 판 위에 자기 돌이 더 많은 사람이 승리

즉 "어디를 차지할까"보다 "어디를 막을까, 언제 열까"가 더 중요한 게임입니다.
이걸 iOS/Android 앱으로 만드는 게 이 프로젝트의 목표입니다.

> 📄 게임 규칙 전체는 `game-rules.md`에 정밀하게 적혀 있습니다. 여기서는 감만 잡으면 됩니다.

## 2. 큰 그림: 왜 이렇게 설계했나요?

앱을 만들 때 "화면 코드"와 "게임 규칙 코드"를 뒤섞어서 짜고 싶은 유혹이 있습니다.
하지만 이 프로젝트는 처음부터 **셋으로 딱 나눠서** 설계했습니다.

```
🖼  화면 (UI)      — 사용자가 보고 만지는 부분
📦  보관함 (Store)  — 지금 게임이 어떤 상태인지 기억하는 곳
🧠  규칙 (Engine)   — "이 수가 맞는 수인가?", "포획이 일어나는가?"를 계산하는 순수한 로직
```

### 왜 굳이 나눴나요?

이 게임은 **혼자 하기(로컬), AI와 대전하기, 온라인으로 다른 사람과 대전하기** 세 가지 모드를 계획하고 있습니다.
세 모드 전부 "포획이 일어나는지, 이 수가 규칙에 맞는지"를 판단해야 합니다.

만약 이 로직을 화면 코드 안에 섞어서 짜면:
- AI를 만들 때 화면 코드에서 규칙 부분만 억지로 뽑아 써야 하고
- 온라인 대전에서 "상대가 정말 규칙대로 뒀는지" 서버가 검사하려면 서버에도 같은 로직을 **또** 짜야 합니다

그러면 화면 코드, AI 코드, 서버 코드에 규칙이 **세 번** 따로 존재하게 되고,
셋 중 하나만 살짝 달라도 "내 화면에선 이겼는데 서버는 졌다고 한다" 같은 버그가 생깁니다.

**그래서 규칙(Engine)을 화면과 완전히 분리된, 독립적인 코드 덩어리로 만들었습니다.**
화면도, AI도, 서버도 전부 이 하나의 Engine을 가져다 씁니다. 규칙은 세상에 딱 한 군데만 존재합니다.

### "순수 함수"라는 게 뭔가요?

Engine 코드는 **순수 함수**로만 짭니다. 처음 듣는 용어라면 이렇게 생각하면 쉽습니다:

> 계산기에 3 + 5를 입력하면 항상 8이 나옵니다. 어제 눌렀든 오늘 눌렀든, 다른 사람이 눌렀든 상관없이요.
> 이게 순수 함수입니다 — **같은 입력이면 항상 같은 결과**, 그리고 계산기 밖의 아무것도 건드리지 않습니다.

반대로 "화면에 표시하기", "서버에 저장하기" 같은 건 순수 함수가 아닙니다 — 외부 세상과 상호작용하니까요.

Engine 함수는 예를 들면 이렇습니다:

```
지금 게임 상태 + "여기에 돌을 놓겠다"
        ↓
   새로운 게임 상태 (포획이 일어났다면 반영된 채로)
```

같은 상태에서 같은 수를 두면 언제, 어디서 실행하든 항상 같은 결과가 나옵니다.
이 덕분에:
- **테스트하기 쉬움** — 입력과 출력만 확인하면 됨
- **AI가 안전하게 미리 계산해볼 수 있음** — "이 수를 두면 어떻게 될까?"를 실제 게임에 영향 없이 시뮬레이션 가능
- **되돌리기(undo)가 쉬움** — 이전 상태를 그냥 기억해두면 됨
- **서버 검증이 쉬움** — 서버도 똑같은 함수를 돌려보면 클라이언트가 거짓말했는지 바로 알 수 있음

> 📄 더 알고 싶다면: `design-spec.md` 1장(레이어 아키텍처), `memory/decisions.md`의 ADR-004

## 3. 데이터는 어떻게 오가나요?

**로컬에서 혼자(또는 같은 기기로 둘이) 플레이할 때:**
```
화면을 탭함 → "이 수를 두겠다" → Engine이 계산 → 결과를 Store가 저장 → 화면이 새로 그려짐
```

**AI와 대전할 때:**
```
AI 차례가 되면 → AI가 Engine을 반복 호출해서 "어떤 수가 제일 좋을까" 탐색
→ 제일 좋은 수를 고름 → 위와 똑같은 흐름으로 진행
```

**온라인으로 대전할 때 (나중에 구현):**
```
내가 수를 둠 → 서버로 "이 수를 두겠다"고 전송 (결과가 아니라 의도만 보냄)
→ 서버가 자기 Engine으로 그 수가 맞는지 재계산 → 맞으면 확정, 틀리면 거부
→ 상대 화면에도 반영
```

여기서 중요한 포인트: **온라인에서는 내 화면이 "내가 이겼다"고 말해도 서버가 다시 계산해서 확인합니다.**
이렇게 안 하면 누군가 앱을 조작해서 자기가 이겼다고 우기는 부정행위(치팅)를 막을 수 없습니다.

> 📄 더 알고 싶다면: `design-spec.md` 6장(온라인 대전 설계)

## 4. 게임 규칙에서 정한 것들 (그리고 왜 그렇게 정했는지)

기획서만으로는 애매한 부분이 몇 개 있었습니다. 예를 들어 "봉인을 복구하면 그 자리는 빈칸인가,
아니면 복구한 사람의 돌이 바로 놓이는가?" 같은 것들이요. 이런 건 코드를 짜기 전에 미리 정해야
나중에 다시 뜯어고치지 않습니다. 다섯 가지를 정했습니다:

| 질문 | 정한 답 | 왜 이렇게 정했나 |
|------|---------|-----------------|
| 봉인을 복구하면? | 빈칸이 됨 | 복구하자마자 돌이 생기면 너무 강력한 능력이 됨 |
| 포획이 연쇄로 일어나나? | 안 일어남, 한 번만 | 규칙이 단순해야 이해하기 쉬움 |
| 둘 곳이 없으면? | 그 턴만 넘기고(패스), 둘 다 연속으로 못 두면 게임 종료 | 잠깐 막혔다고 바로 게임을 끝내면 역전 기회가 사라짐 |
| 새 칸은 아무거나 열 수 있나? | 보드에 미리 정해둔 후보 중에서만 | 보드 설계자가 의도한 확장만 허용 |
| 포획당한 돌은 어디로 가나? | 영구히 사라짐 | 포획의 긴장감을 극대화 — 체스에서 말을 잃는 느낌과 비슷 |

**마지막 항목이 좀 특이합니다.** 돌이 영구히 사라지면 게임이 너무 매섭게 느껴질 수도 있어서,
"혹시 너무하면 이렇게 바꾸자"는 대안(포획당한 돌을 결정으로 다시 살 수 있게)도 미리 코드에
설정값으로 심어뒀습니다. 실제로 AI끼리 수백 판을 시켜보고 데이터로 판단할 예정입니다.
감으로 정하지 않고, 숫자를 보고 정하겠다는 뜻입니다.

> 📄 더 알고 싶다면: `game-rules.md` (규칙 전체), `memory/decisions.md`의 ADR-008/009

## 5. 폴더 구조 — 어디서부터 봐야 하나요?

프로젝트가 만들어지면 이런 모습일 겁니다 (아직 코드는 없고, 설계만 끝난 상태입니다):

```
seal/
├── app/                # 화면들 (사용자가 실제로 보는 것)
├── src/
│   ├── engine/         ⭐ 여기부터 보세요 — 게임 규칙의 전부
│   ├── ai/             # AI 상대 (engine을 가져다 씀)
│   ├── store/           # 지금 게임 상태를 기억하는 곳
│   ├── net/             # 온라인 대전 통신
│   └── components/      # 화면에 그려지는 부품들 (판, 돌 등)
├── boards/              # 게임판 모양 데이터 (JSON 파일)
├── locales/             # 한국어/영어 화면 문구
└── functions/           # 온라인 대전 서버 코드
```

**처음 코드를 볼 사람에게 추천하는 순서:**
1. `game-rules.md`를 먼저 읽고 규칙을 이해하기
2. `src/engine/types.ts` (만들어지면) — 게임 상태가 어떤 모양의 데이터인지
3. `src/engine/` 안의 함수들 — 규칙이 실제로 어떻게 코드가 됐는지
4. `src/engine/__tests__/` — 테스트를 보면 "이 함수가 어떤 상황에서 어떻게 동작해야 하는지" 예시로 알 수 있음
5. 그다음에 `store/`, `components/` 순서로

**규칙 코드(`engine/`)를 건드릴 때 지켜야 할 것:**
- React나 Firebase 관련 코드를 여기에 절대 넣지 않기 (섞이면 §2에서 설명한 장점이 다 깨짐)
- 함수는 항상 "새로운 상태"를 반환하고, 기존 상태를 직접 고치지 않기

> 📄 더 알고 싶다면: `design-spec.md` 7장(폴더 구조)

## 6. 용어집

### 게임 용어

| 용어 | 뜻 |
|------|-----|
| 노드 | 판 위에서 돌을 놓을 수 있는 한 지점 |
| 포획 | `내 돌 – 상대 돌 – 내 돌` 모양이 되면 가운데 상대 돌을 없애는 것 |
| 봉인 | 포획이 일어난 자리가 못 쓰게 되는 것 (X 표시) |
| 결정 (💎) | 포획할 때마다 얻는 자원. 세 가지 능력에 쓸 수 있음 |
| 핵심 노드 | 돌 개수가 같을 때 승부를 가르는 특별한 자리 |

### 기술 용어

| 용어 | 쉬운 설명 |
|------|-----------|
| Engine | 게임 규칙만 모아둔 코드 덩어리. 화면이나 서버와 상관없이 독립적으로 동작 |
| 순수 함수 | 같은 입력이면 항상 같은 결과가 나오고, 다른 곳에 영향을 안 주는 함수 (§2 참고) |
| GameState | "지금 게임이 어떤 상태인지"를 담은 데이터 한 덩어리 (누가 어디 있는지, 결정이 몇 개인지 등) |
| Move | "이런 수를 두겠다"는 의도를 담은 데이터 (예: "여기에 돌 놓기") |
| Store | 화면에서 쓸 수 있게 GameState를 기억해두는 곳 (Zustand라는 도구 사용) |
| 서버 권위 | 온라인 대전에서 "누가 이겼는지" 최종 판단은 항상 서버가 한다는 원칙 |
| ADR | "왜 이렇게 결정했는지"를 기록해둔 문서 (Architecture Decision Record) |

> 📄 게임 용어 전체 목록은 `memory/glossary.md`에 더 있습니다.

## 7. 어떤 순서로 만들어지나요?

한 번에 다 만들지 않고 단계별로 쌓아 올립니다. 각 단계가 끝나면 그 전 단계는 계속 동작해야 합니다.

| 단계 | 목표 | 끝나면 뭐가 되나요? |
|------|------|---------------------|
| **M0 — 기반** | 프로젝트 뼈대 만들기 | 앱이 실행은 되지만 아직 게임은 안 됨 |
| **M1 — 규칙 엔진** | 게임 규칙을 코드로 완성 | 📱 **같은 기기로 둘이 번갈아 플레이 가능** ← 이게 사실상 첫 완성판 |
| **M2 — AI** | 혼자서도 할 수 있게 | 컴퓨터와 대전 가능, 애니메이션 추가 |
| **M3 — 온라인** | 다른 사람과 대전 | 실시간 온라인 대전 가능 |
| **M4 — 출시** | 스토어에 올리기 | 앱스토어/플레이스토어 출시 |

**M1이 끝나는 시점이 중요합니다.** 그때부터 "이 게임이 정말 재미있는가?"를 실제로 사람이 플레이하며
확인할 수 있습니다. 그 전까지는 눈에 보이는 게임이 없습니다.

> 📄 각 단계의 세부 할 일은 `roadmap.md`와 `tasks/backlog.md`에 있습니다.

## 8. 미리 대비해둔 위험 요소

만들다 보면 예상 못 한 문제가 생기기 마련이지만, 몇 가지는 시작 전부터 눈에 보여서 미리 대비해뒀습니다.

**"포획당한 돌이 영구히 사라진다"는 규칙이 너무 가혹할 수 있음**
→ 3번 포획당하면 돌이 5개에서 2개로 줄어듭니다. 결정을 아무리 모아도 놓을 돌이 없으면 소용없어질 수 있습니다.
→ 대비: 코드에 "설정값 하나만 바꾸면 다른 규칙으로 전환"할 수 있게 만들어뒀습니다.
   AI끼리 자동으로 수천 판을 시켜보고 실제로 문제가 되는지 숫자로 확인할 예정입니다.

**AI가 다음 수를 고민하는 동안 화면이 멈출 수 있음**
→ 여러 수를 앞서 계산해보는 AI는 계산량이 많아서, 스마트폰에서 자칫 화면이 버벅일 수 있습니다.
→ 대비: 계산을 한 번에 몰아서 하지 않고 나눠서 실행하도록 설계했습니다. 저사양 기기에서 실측해서 난이도를 조정할 예정입니다.

**혼자 만드는 프로젝트라 욕심이 과해질 수 있음**
→ 기능을 계속 추가하고 싶어지는 건 자연스러운 유혹입니다.
→ 대비: `roadmap.md`에 "이번 버전에서는 안 할 것" 목록을 명시적으로 적어뒀습니다.

## 9. 아직 안 정한 것들 (그런데 괜찮은 이유)

몇 가지는 일부러 지금 안 정했습니다. 지금 정해도 의미가 없거나, 실제로 만들어봐야 알 수 있는 것들이라서요.

| 안 정한 것 | 언제 정하나요? | 왜 지금 안 정해도 되나요? |
|-----------|---------------|--------------------------|
| 게임판의 정확한 모양 | 첫 게임판 만들 때 | 실제로 그려보고 밸런스를 봐야 함 |
| AI가 얼마나 똑똑해야 하는지 | AI 만들 때 | 만들어보고 튜닝하는 게 정상적인 순서 |
| "돌 영구 소멸" 규칙 유지 여부 | AI끼리 대전 데이터를 본 후 | §8에서 설명한 것처럼 데이터로 판단 |
| 온라인 연결 끊김 대기 시간 | 온라인 기능 만들 때 | 그 전까지는 필요하지 않은 값 |

이것들은 전체 설계에 영향을 주지 않는 "숫자만 나중에 채우면 되는" 항목이라, 지금 만들기를 미룬다고
해서 나중에 뜯어고쳐야 하는 일은 없습니다.
